# Next Card AI 行为规约

这份文档是 Next Card 的 **AI 决策知识库**。它回答一个问题：

> 用户输入一段文字、附件或图片课表后，AI 要按什么规则判断、拆解、产出，才能让前端组件正确渲染。

它**不**是前端交互手册（手势阈值、动画时长那些），那部分需要时再单独写。

读者：当前的 `lib/mock-ai.ts`、未来要替换它的真实 LLM，都遵守这份规约。前端是"消费者"，规约是"生产者必须满足的契约"。

---

## 0. 必须先理解的事：前端 = AI 的硬性输出契约

前端组件已经把 AI 该输出什么形态、几条、几个字段、什么类型完全锁死。AI 不能临场决定"这次多生成一条方案"或"这次省掉时间锚"。

| 前端组件/字段 | 强制 AI 必须输出 |
|---|---|
| `PlanModePanel` 的 TimeChip × 3 | `deadlineLabel / availableWindow / suggestedStart` 三个**非空**字符串 |
| `PlanModePanel` 的 InfoBlock | `constraints[]` 与 `timeStrategy[]` 各 **3 条左右** |
| `PlanOptionCard` × 3 | 必须**恰好 3 个**方案，分别 `urgent / balanced / gentle`，按下标渲染"方案一/二/三" |
| 每个 `PlanOption` | `estimatedTime` 字符串、`detailLevel` 三档之一、`steps[]` **4 步** |
| `TaskFlowOverview` | 节点最多 4 个（代码硬切），每节点必带 `timeLabel` 与 `urgencyStage` |
| `DeckLibrary` 卡片堆 | 卡组最多 6 张卡（代码硬切） |
| `SwipeTaskCard` | 每卡必带 `title / action / estimatedMinutes / encouragement / cardBackNote / urgencyStage / damageEffect` |
| `CardTimeUI` | 必带 `estimatedMinutes` 与时间窗口标签（`deadlineAt` 有就算"剩 N min"，没有就 `建议现在开始 / 今天内`） |
| `DeckStatusBar` | 推断的 `urgencyStage` 必须是 `calm/warm/hot/burning/expired` 五取一 |
| `FreezePrompt` | 任何时候用户可以冻结，所以**任何卡都必须可冻结**（不能输出"必须现在做不能停"的卡） |

**违反契约 = 前端崩溃或显示空白**。比如方案返回 2 条会让"执行方案三"按钮指向 `undefined`；timeLabel 漏写会让节点显示空字符串。

## 1. 任务复杂度判定（决定生成什么）

这是规约的第一层判断。所有输入都先过这一步。

### 1.1 三类任务

| 类型 | 定义 | 输出形态 |
|---|---|---|
| **元任务** | 一次连续动作可完成、无内部阶段、完成与否一眼可判、不依赖其他前置 | 1 张卡，最多 2 张（动作 + 收尾） |
| **简单复杂任务** | 单一目标，但需要 2-3 个阶段 / 不同 context | 3-4 张卡，1 个 task flow 节点序列 |
| **多阶段复杂任务** | 跨时间、跨场景、有里程碑或多源依赖 | 4-6 张卡（前端上限 6），多节点 task flow，可能含燃烧演示首卡 |

### 1.2 判定信号（按权重）

按以下信号打分，命中越多越复杂：

| 信号 | 含义 | 命中即视为"复杂" |
|---|---|---|
| 时间跨度 | 输入提到"明天/下周/这学期/月底" | ✓ |
| 多个动词 | "复习并整理并默写" | ✓ |
| 多个对象 | "数学和英语""作业、PPT、邮件" | ✓ |
| 大目标关键词 | "考试 / 项目 / 论文 / 答辩 / 比赛 / 演讲" | ✓✓ |
| 多源输入 | text + attachment、text + image | ✓ |
| 时间长度 | 输入预估 > 30 分钟 | ✓ |
| 单步动词 + 单对象 + 短描述 | "把书放进包里" | 元任务 |

**示例对照**：

| 输入 | 类型 | 理由 |
|---|---|---|
| `把作业页放进包里` | 元任务 | 单动词单对象，3 分钟内完成 |
| `去高数课` | 简单复杂 | 隐含"准备 → 出门 → 到达"三阶段 |
| `今晚 20:00 前交一页课程分析` | 简单复杂 | 单一目标但要"读要求 → 草稿 → 检查" |
| `明天考数学` | 多阶段复杂 | "考试"关键词 + 跨日 + 隐含多科目动作 |
| `这周要把毕设答辩准备好` | 多阶段复杂 | 大目标 + 时间跨度 + 多里程碑 |

### 1.3 复杂任务的拆解规则

复杂任务必须先拆成"元任务序列"，每个元任务再独立成卡。拆解时遵守：

- **每张卡 = 一个明确动作**，不是"复习数学"这种描述。坏例子见 §6.1。
- **首卡必须是最低启动门槛动作**：3-10 分钟内能做完的"打开/确认/圈出/写下"类动作。这是"启动 - 推进 - 收尾"节奏的入口。
- **末卡必须是收尾留证动作**：写下下一次继续的上下文、保存草稿、对照检查。让 deck 有清晰终点。
- **避免重复 context**：相邻两卡不要都是"打开课本"这种相同前置动作。

## 2. 触发轨道库（决定按哪套模板生成）

输入归类后落到一条**轨道**，每条轨道有自己的卡组模板、时间策略、首卡是否燃烧。

### 2.1 现有 + 新增轨道清单

| 轨道 ID | 触发关键词 | 任务复杂度倾向 | 首卡是否燃烧演示 | 时间策略基调 |
|---|---|---|---|---|
| `course` | 高数 / 课程 / 上课 / 课表 / 早八 / 教室 | 简单复杂 | **是**（4 min, burnLevel:3, damageProgress 68→84） | 现在 → 出门 → 到达 |
| `assignment` | 作业 / 提交 / 截止 / 论文 / 报告 / ddl / deadline | 简单/多阶段 | 否（除非剩余时间 ≤ 20min） | 最低可交 → 补充 → 检查 |
| `exam` ★新增 | 考试 / 考研 / 考期 / 期末 / 期中 / 月考 / 模考 / 答辩 | **多阶段复杂** | 否（考试是长程任务，不该一上来就燃烧） | 范围确认 → 错题 → 默写/串讲 → 过公式 → 临考检查（详见 §2.5） |
| `routine` ★新增 | 收拾 / 整理 / 出门 / 通知 / 回复 / 吃药 / 喝水 / 睡前 / 起床 | **元任务** | 否 | 现在做完即可 |
| `project` ★新增 | 项目 / 答辩 / 比赛 / 演讲 / 提案 / 设计稿 / 上线 | **多阶段复杂** | 否 | 拆里程碑 → 主推进 → 收尾留证 |
| `learning` ★新增 | 学 / 复习 / 预习 / 背 / 默 / 刷题 / 看书 / 读论文 | 简单/多阶段 | 视截止时间而定 | 选材 → 单元推进 → 自测 |
| `default` | 都不命中 | 按 §1 复杂度判定决定 | 否 | 25 分钟内启动第一张卡 |

★= 当前 `mock-ai.ts` 没有的，要补。

### 2.2 多轨道命中怎么办

按上表**从上往下**取第一个命中的。`exam` 优先于 `learning`（"考研复习"先归考试轨），`assignment` 优先于 `project`（"项目作业截止"先归作业轨）。

如果输入既有 `course` 又有 `assignment`（例如"明天高数课交作业"），按 `course` 走但首卡换成"先确认作业要带的版本"。

### 2.3 元任务轨道（routine）的特例

元任务**不生成 plan options**。或者说：三个方案的 steps 完全相同，只是 `estimatedTime` 微调。前端虽然必须显示 3 个方案，但内容上可以让用户感觉"AI 觉得这事不需要选方案"。

替代方案：让 AI 在 `goalUnderstanding` 里直接说"这是一步就能完成的事，三套方案只在节奏上略有不同"，避免显得啰嗦。

### 2.4 新轨道扩展约束

加新轨道时，必须同时给出：
1. 触发关键词清单（≥3 个，要覆盖中英文常见说法）
2. 卡组模板：4 步 steps × 三个方案
3. 时间策略基调（3 句话）
4. 默认时间锚（`deadlineLabel / availableWindow / suggestedStart`）
5. 首卡是否燃烧演示的规则
6. 一组反例（什么输入**不**该归到这个轨道）

### 2.5 考试轨拆解模板

考试是 Next Card 必须做对的"招牌例子"。对齐结果如下：

#### 卡数与跨度

固定 **5 张卡，跨 2 天**：3 张今晚 + 2 张明天临考前。

| # | 卡 title | 触发时间 | estimatedMinutes | 阶段含义 |
|---|---|---|---|---|
| 1 | 确认{科目}考试范围和题型 | now（今晚启动） | 20 | 范围确认 |
| 2 | 扫一遍最近的错题/作业，圈出 3 个最不熟的点 | now + 30min | 25 | 错题 / 弱点定位 |
| 3 | 把这 3 个点对应的公式或要点写一遍（不要看一眼） | now + 90min | 20 | 默写 / 串讲 |
| 4 | 早上花 10 分钟过一遍公式和易错点 | 明天 8:00 | 10 | 过公式 |
| 5 | 临考前检查文具/准考证/路线 | 考前 30min | 5 | 临考检查 |

> 这是 `balanced` 方案。`urgent`/`gentle` 按 §4.3 时间倍数缩放，但**卡片骨架不变**——5 张、跨 2 天。

#### 首卡选择规则（动态）

由 AI 根据用户输入时与考试的剩余时间决定，**不是固定第一张**：

| 距考试 | 首卡（用户首次进入 deck 看到的那张） |
|---|---|
| > 12 小时 | 第 1 张：确认范围 |
| 2 - 12 小时 | 第 4 张：过公式 |
| ≤ 2 小时 | 第 5 张：临考检查 |
| 已过考试时间 | 不生成考试轨，提示用户改日复盘 |

实现时：5 张卡都生成，但 `status: "active"` 打在合适的那张上，前面已经"过期"的几张直接 `status: "completed"` 但带提示文案"未走过此卡"，避免用户被旧卡卡住。

#### urgencyStage 推进（按考前剩余时间跳）

考试轨**不按卡位置**判 urgency，**按距离考试时间**判。所有未完成卡共享同一个 stage：

| 距考试 | 全卡 urgencyStage |
|---|---|
| > 12 小时 | `calm` |
| 12 - 6 小时 | `warm` |
| 6 - 2 小时 | `hot` |
| 2 - 0.5 小时 | `burning` |
| ≤ 0.5 小时 | `burning`（且 damageProgress = 95） |
| 已过 | `expired` |

这意味着用户今晚 22:00 看到的卡是 `calm`，第二天早 6:00 自动跳 `warm`，7:30 跳 `hot`。需要前端在 deck mount 时启动一个 tick（参见前端 §6 Gap G2），或者在每次打开 deck 时刷新一次 stage。

#### 反例

下列输入**不**走考试轨，避免误归类：

| 输入 | 该归 | 为什么 |
|---|---|---|
| `准备一下面试` | project | 面试不是考试，节奏更长 |
| `复习一下昨天的课` | learning | 是日常复习不是考前 |
| `背一下英语单词` | learning | 不含截止时间点 |
| `测试一下这段代码` | default 或 project | "测试"歧义，不命中考试关键词 |

### 2.6 routine 轨拆解模板

routine 是元任务的主要承载轨道。原则：**少即是多**，不要把"喝水"拆成 5 步。

#### 卡数（动态 1-3 张）

由 AI 根据输入的动作复杂度决定：

| 输入特征 | 卡数 | 例 |
|---|---|---|
| 单动词 + 单对象 + 无依赖 | 1 张 | `吃药` `喝水` `回邮件给小李` |
| 单动词 + 多对象 / 单动词 + 简单依赖 | 2 张 | `回复今天的几条通知` → ①圈出必回的 ②逐条回 |
| 复合动词 / 出门类带准备 | 3 张 | `出门取快递` → ①确认地点和码 ②穿好出门 ③回来归位 |

**3 张是上限**。再多就该升到简单复杂任务（routine 不是 routine 了）。

#### 三方案差异化（仅启动语气）

routine 的三个方案 **steps 完全相同**，只在 estimatedTime 和 summary 上微调启动语气：

| 方案 | summary 措辞 | estimatedTime 措辞 |
|---|---|---|
| urgent | "现在马上做完，不要拖到下一件事打断它。" | `现在 / 2 min` |
| balanced | "5 分钟内启动，做完就过。" | `5 min` |
| gentle | "今天抽空做，不到睡前都行。" | `今天内 / 弹性 8 min` |

goalUnderstanding 必须含一句"这是一步就能完成的事，三套方案只在节奏上略有不同"，避免用户觉得 AI 把小事讲复杂。

#### 首卡选择规则

routine 卡数少（1-3），不需要动态首卡。**第 1 张永远是首卡**。

#### urgencyStage（看输入语气）

routine 不按时间衰减，按用户**输入里的时间词**一次性决定，所有卡共享：

| 输入命中 | urgencyStage |
|---|---|
| `马上 / 现在 / 立刻 / 立马 / 赶紧` | `hot` |
| `5 分钟内 / 一会儿 / 等会` | `warm` |
| `今天 / 抽空 / 有空 / 顺手` | `calm` |
| 没有时间词 | `calm` |

routine 轨**永不进入 burning 或 expired**。即使用户半天没点击，也保持原 stage。这是产品决策：routine 是日常事，逾期不该被惩罚，下次想起来再做即可。

#### damageEffect

routine 全部 `none`。不演示燃烧、不演示裂痕。冻结仍可由用户手动触发（前端 FreezePrompt 不锁），冻结后变 `freeze`。

#### 反例

| 输入 | 该归 | 为什么 |
|---|---|---|
| `今天要把房间整理一下` | default 或 project | "整理房间"含多动作多区域，不是元任务 |
| `准备一下出差` | project | 出差准备含多源依赖（机票/行程/物品） |
| `把这个月的发票报销了` | assignment | 含截止流程，不是即时动作 |
| `学一下今天的课` | learning | 是学习不是日常 |

### 2.7 learning 轨拆解模板

learning 覆盖"日常学习/复习/预习"，跟 exam 的区别：**没有明确考试节点**，是持续推进。

#### 卡数

固定 **3-4 张**，单次学习单元。不要做成"一周复习计划"——那是 project。

| 输入特征 | 卡数 | 阶段 |
|---|---|---|
| 简单复习 / 单一材料 | 3 张 | 选材 → 推进 → 自测 |
| 跨章节 / 跨教材 | 4 张 | 选材 → 第一单元 → 第二单元 → 自测 |

每张卡 estimatedMinutes 在 15-25 之间。**首卡必须 ≤ 15 min**（启动门槛）。

#### 三方案差异化

| 方案 | 核心差异 |
|---|---|
| urgent | 4 步压缩到 30-40 min，跳过自测，先看完再说 |
| balanced | 标准 4 步，含自测 |
| gentle | 4 步拉到 75-90 min，允许"只做第一段就停"，第 4 步初始 frozen |

#### 首卡选择规则

learning **第 1 张永远是首卡**（不像 exam 看时间动态选）。原因：learning 没有硬截止，"现在开始"永远是对的。

#### urgencyStage

learning 不依赖外部时间，按**卡片在 deck 里的位置**判：

| 卡位置 | urgencyStage |
|---|---|
| 第 1 张（启动卡） | `warm`（轻轻推一下） |
| 中段 | `calm` |
| 末张（自测卡） | `calm` |
| 用户启动后 25 min 仍在第 1 张 | 升到 `hot`（提醒别卡在启动） |

#### damageEffect

| 条件 | effect |
|---|---|
| 启动后 > 25min 仍未推进 | `burn`，burnLevel 1，提醒不是惩罚 |
| 创建后 > 3 天未触碰 | `weathering` |
| 否则 | `none` |

learning 是少数会真正用到 `weathering` 的轨道——长期搁置的复习卡需要被"看到"。

#### 反例

| 输入 | 该归 | 为什么 |
|---|---|---|
| `明天考英语` | exam | 有考试节点 |
| `做一下高数作业` | assignment | 有提交动作 |
| `读一篇 paper 然后写综述` | project | 含产出物 |
| `复习一下今天的课` | learning ✓ | 标准命中 |

### 2.8 project 轨拆解模板

project 覆盖大型多里程碑任务：答辩、比赛、提案、设计稿、发布。**最重的轨道**。

#### 卡数

固定 **6 张**（前端上限）。每张代表一个里程碑，不是一个动作——所以 project 卡的 estimatedMinutes 比其他轨道大。

| # | 阶段含义 | estimatedMinutes |
|---|---|---|
| 1 | 拆里程碑 / 列出产出物 | 25 |
| 2 | 第一里程碑：起草 / 调研 | 40 |
| 3 | 第二里程碑：主体推进 | 45 |
| 4 | 第三里程碑：完善关键部分 | 35 |
| 5 | 收尾：检查 / 打磨 | 25 |
| 6 | 留证：交付 / 发布 / 演练一遍 | 20 |

#### 三方案差异化

| 方案 | 核心差异 |
|---|---|
| urgent | 砍卡 4 和 5，只留 4 张：拆 → 主推 → 完善 → 交付。压缩到 1 个工作日 |
| balanced | 完整 6 张，分布在 3-5 天 |
| gentle | 完整 6 张，第 4-5 张初始 frozen，分布在 1-2 周 |

#### 首卡选择规则

由 AI 根据用户**距交付的剩余时间**和**已完成卡数**选：

| 状态 | 首卡 |
|---|---|
| 新建 deck | 第 1 张（拆里程碑） |
| 已完成里程碑 1 / 距交付 > 3 天 | 第 2 张 |
| 已完成里程碑 1-3 / 距交付 ≤ 3 天 | 第 4 张（完善关键部分） |
| 距交付 ≤ 1 天 | 第 5-6 张（收尾 / 留证） |

project 是 Next Card 唯一会**多次回访 deck** 的轨道，所以首卡每次打开都重新算。

#### urgencyStage（按距交付时间跳，类似 exam 但门槛更宽）

| 距交付 | 全卡 urgencyStage |
|---|---|
| > 5 天 | `calm` |
| 5 - 2 天 | `warm` |
| 2 - 1 天 | `hot` |
| ≤ 24 小时 | `burning` |
| 已过 | `expired` |

#### damageEffect

| 条件 | effect |
|---|---|
| 距交付 ≤ 1 天且未完成 | `burn`，burnLevel 2-3 |
| 用户冻结 | `freeze` |
| 已过交付时间 | `crack` |
| 创建后 > 7 天未推进 | `weathering` |

#### 反例

| 输入 | 该归 | 为什么 |
|---|---|---|
| `明天考试` | exam | 考试有专属轨道 |
| `今晚交作业` | assignment | 单次提交 ≠ 多里程碑 |
| `准备一下今天的会` | routine 或 default | 临时会议不到 project 体量 |
| `做毕业答辩 PPT` | project ✓ | 多里程碑 + 交付物 |

## 3. goalUnderstanding 写法规则

这一段是用户最早看到的 AI 输出，决定"AI 显得懂不懂我"。

### 3.1 必须满足的三件事

1. **不是回显**。用户写"明天考数学"，**不能写**"你要明天考数学"。要写"你想把这次考试从一个模糊压力变成可以分天推进的复习节奏"——**重新框定**。
2. **指出隐含动作**。把用户没说出口但显然要做的事点出来：去高数课 → 重点不是"记得上课"而是"准备/出门/到达"。
3. **保留温度**。不用"任务""目标""执行"这种生硬词，用"想推进""把它变成""开始的第一步"这类。

### 3.2 句式模板

```
你想把「{用户输入精简版}」从{当前模糊状态}变成{具体可执行形态}。
重点不是{用户表面说的那件事}，而是{隐含的真正动作}。
```

例：

| 输入 | goalUnderstanding |
|---|---|
| `去高数课` | 你想把「去高数课」从一句提醒变成可以马上执行的出门/到课卡组。重点不是"记得上课"，而是把准备、离开、到达和课前缓冲拆开。 |
| `明天考数学` | 你想把「明天考数学」从一片焦虑变成今天可以推进的最低复习节奏。重点不是"全部复习一遍"，而是先确认范围、找到最薄弱处、做一次最小自测。 |
| `今晚交一页分析` | 你想把「今晚交一页分析」变成一组最低可提交优先的行动卡。重点是先保护交付线，再处理润色和检查。 |

### 3.3 长度

中文 50-90 字。两句到三句。短了显得敷衍，长了 PlanModePanel 的 `font-editorial` 标题区会换行难看。

## 4. 三方案差异化规则

前端必须 3 个方案，分别 `urgent / balanced / gentle`。这三个方案不是简单的"快/中/慢"，是**三种不同的执行哲学**。

### 4.1 三方案的语义差

| 方案 | 哲学 | 适用心境 | 时间倍数（相对 balanced） | detailLevel |
|---|---|---|---|---|
| `urgent` | 保护"最小可交付"，先有再优 | 时间紧、已临窗口、想立刻动起来 | × 0.6 | high（步骤具体到动词） |
| `balanced` | 速度与完整度平衡，节奏稳定 | 正常推进、有空、想做扎实 | × 1.0 | medium |
| `gentle` | 允许冻结、允许中断、保留出口 | 疲劳、焦虑、长期目标、低能量 | × 1.4 | low（步骤宽泛留余地） |

### 4.2 steps 的写法差

每个方案 4 步。同一目标三个方案的 steps **必须不一样**——不是同样的 4 步换个 estimatedTime。

以"今晚 20:00 前交一页课程分析"为例：

| Step | urgent | balanced | gentle |
|---|---|---|---|
| 1 | 圈出必须完成的 3 个点 | 读一遍要求 | 写下任务边界 |
| 2 | 用 10 分钟做最低可交版本 | 拆出主要段落或模块 | 只做第一个小段 |
| 3 | 补上一个最关键细节 | 完成主体草稿 | 冻结不必要分支 |
| 4 | 快速检查并提交或保存证据 | 检查格式和遗漏 | 留下下一次继续的上下文 |

注意 gentle 第 3 步"冻结不必要分支"——**主动暗示用户用冻结手势**，与前端 FreezePrompt 呼应。urgent 不出现"冻结"二字，因为它的哲学是"先做完"。

### 4.3 估时规则

- urgent ≈ balanced × 0.6（向下取整到 5 分钟倍数）
- gentle ≈ balanced × 1.4（向上取整到 5 分钟倍数）
- balanced 由轨道默认值决定：course=28min, assignment=45min, exam=60min, project=60min, routine=8min, learning=45min, default=45min

### 4.4 summary 文案模板

每个方案都需要一句 summary（PlanOptionCard 显示）。模板：

```
urgent:   "先保护{核心可交物}，适合时间紧或已经接近最佳窗口时使用。"
balanced: "速度和完整度平衡，适合正常推进，卡片节奏更稳定。"
gentle:   "低压力版本，允许中途冻结，适合{疲劳/焦虑/长期目标}。"
```

## 5. 时间锚点推导规则

前端三个 TimeChip：`deadlineLabel / availableWindow / suggestedStart`。AI 必须填三个，**绝对不能为空字符串**。

### 5.1 有明确时间时

输入里出现具体时间（"今晚 20:00"、"明天早八"、"3 小时内"），按 §5.3 规则化。

### 5.2 无明确时间时的默认值表

| 轨道 | deadlineLabel | availableWindow | suggestedStart |
|---|---|---|---|
| course | 还有 18 分钟到最佳出门窗口 | 现在到课前 20 分钟 | 现在开始第一张卡 |
| assignment | 今晚 20:00 前 | 今天晚饭前到 20:00 | 建议 25 分钟内启动 |
| exam | 考前 {N} 天 | 今天 + 接下来每天的复习窗口 | 今晚先做范围确认 |
| routine | 现在做完 | 接下来 5-10 分钟 | 现在 |
| project | 截止 {N} 天前完成主体 | 本周 + 下周 | 今天先确认里程碑 |
| learning | 今天内 1 个单元 | 接下来 45-60 分钟 | 25 分钟内 |
| default | 今天内完成第一轮推进 | 接下来 25-45 分钟 | 25 分钟内开始 |

`{N}` 是用户提到的天数；没提就给"今晚/明天"。

### 5.3 时间表达规则

- **deadlineLabel** 必须是"压力感"的，不是"客观时间"。写"还有 18 分钟"而不是"19:42"。
- **availableWindow** 是"窗口"概念，要有起点终点。"现在到 20:00""接下来 25-45 分钟"。
- **suggestedStart** 是"现在该不该开始"。"现在""25 分钟内""今晚饭后"。

### 5.4 卡片级时间字段

每张卡的 `deadlineAt / suggestedStartAt / estimatedMinutes` 由 §7 卡片字段决策树决定。

## 6. 卡片字段决策树

每张卡必须填这些字段，下面按字段说决策规则。

### 6.1 title（卡片标题）

**必须是动作短语，不是描述短语**。前端 SwipeTaskCard 用 `font-editorial` 大字号渲染，含糊的标题会非常显眼。

| 好例 | 坏例 | 区别 |
|---|---|---|
| `确认高数课时间和教室` | `复习数学` | 动作明确 |
| `用 10 分钟写出最低可提交版本` | `写作业` | 包含可验证的范围 |
| `把课程表里的明天早八课程加入今日提醒` | `安排提醒` | 对象具体 |

5-15 字。超过 15 字就拆。

### 6.2 action（一句动作指令）

补充 title。回答"具体要做什么"。20-35 字。

模板（按 title 的关键词分支，参考现有 `mock-ai.ts` 的 `makeAction`）：

```
title 含 "确认"   → "打开来源信息，圈出{时间/地点/必须完成的一个动作}。"
title 含 "整理"   → "只拿必须物品，放到一个固定位置，不扩展整理范围。"
title 含 "最低"   → "用 10 分钟写出最低可提交版本，不做润色。"
title 含 "复习"   → "只看 1 个章节，圈出 3 个不会的点，不展开。"
title 含 "默写/背" → "选 5 个最不熟的，写到纸上而不是看一眼。"
其他              → "完成这一步里最小、最明确的动作，然后立刻进入下一张卡。"
```

### 6.3 estimatedMinutes（估时）

按轨道 + 卡片位置决定。**不能用 `index%2 ? 8 : 10` 这种纯位置算法**——AI 应当根据 action 的实际工作量给。

| 轨道 | 典型估时区间 | 首卡（启动卡） |
|---|---|---|
| course | 3-12 min | 4 min（出门类） |
| assignment | 8-15 min | 10 min（读要求） |
| exam | 15-30 min | 20 min（范围确认） |
| routine | 2-5 min | 3 min |
| project | 20-45 min | 25 min |
| learning | 15-25 min | 15 min |

### 6.4 deadlineAt / suggestedStartAt

- 用户明确给了时间 → 用之
- 课程轨首卡 → `deadlineAt = now + 8min`（制造燃烧演示窗口）
- 作业轨 → `deadlineAt = 今晚 20:00`（除非用户给了别的）
- 考试轨 → 各卡分布在"今晚 / 明早 / 临考前"，不集中在一点
- 元任务 → 不需要 deadlineAt，`suggestedStartAt = now`
- 都不知道时 → 第一张 `suggestedStartAt = now`，后续 `now + index * 12min`

### 6.5 urgencyStage（紧迫度）

5 取 1。决策规则：

| 条件 | stage |
|---|---|
| `deadlineAt` 已过 | `expired` |
| 距离 `deadlineAt` ≤ 3 min | `burning` |
| 距离 `deadlineAt` ≤ 20 min | `hot` |
| 距离 `deadlineAt` ≤ 60 min 且是首卡 | `warm` |
| 其他 | `calm` |

**首卡特例**：课程轨首卡强制 `burning`（即使时间充裕也演示），让用户第一次看到燃烧效果。这是产品决策不是 bug。

### 6.6 damageEffect（伤害效果）

| 条件 | effect |
|---|---|
| `urgencyStage === burning` 或 `hot` 且时间紧 | `burn` |
| 用户冻结过 | `freeze` |
| `urgencyStage === expired` | `crack` |
| 卡片创建至今 > 7 天 未触碰 | `weathering` |
| 否则 | `none` |

优先级：`freeze > burn > crack > weathering > none`（前端按这个判断渲染）。

### 6.7 burnLevel / damageProgress

仅当 `damageEffect === burn` 时有意义。

| urgencyStage | burnLevel | damageProgress |
|---|---|---|
| warm（带 burn） | 1 | 30 |
| hot | 2 | 52 |
| burning | 3 | 86 |
| 课程轨首卡演示 | 3 | 68（可慢慢动画到 84） |

### 6.8 encouragement（卡正面安抚语）

短句，10-20 字。语气**不卖惨不亢奋**，像朋友在旁边。

模板：

```
首卡：     "先做这一小步，后面会变轻。"
中段：     "这张卡只需要一个明确动作。"
尾卡：     "你已经走到收尾，这一步比开始那一步轻。"
燃烧卡：   "时间在烧，但你只要做最小动作就够。"
冻结后恢复："你之前停在这里，可以从这一步继续。"
```

### 6.9 cardBackNote（卡背）

下滑显示，30-50 字。给"为什么这一步重要"或"为什么可以放下"的解释。

模板：

```
燃烧卡：   "你不是在赶完整目标，只是在保护最佳行动窗口。"
普通卡：   "继续或冻结都可以，系统会保存上下文。"
冻结候选： "这张卡可以晚点做，但留下一句话标记你想继续。"
```

## 7. Task Flow 节点规则

最多 4 个节点（前端硬切）。节点对应"阶段"，不是"卡片"。一个节点可以包含多张卡。

### 7.1 节点数

| 复杂度 | 节点数 |
|---|---|
| 元任务 | 1 |
| 简单复杂 | 2-3 |
| 多阶段复杂 | 3-4 |

### 7.2 timeLabel 写法

按方案风格切换：

| 方案 style | 第 1 节点 | 第 2 节点 | 第 3 节点 | 第 4 节点 |
|---|---|---|---|---|
| urgent | 还有 18 分钟 | 还有 12 分钟 | 最后窗口 | — |
| balanced | 25 分钟内 | 今晚前 | 收尾前 | — |
| gentle | 今天内 | 明天前 | 后续推进 | 留待复盘 |

### 7.3 节点 status 初始值

- 第 1 个：`active`，progress = 12（让用户看到"已经开始的感觉"）
- 其他：`not-started`，progress = 0
- 例外：`gentle` 方案的第 4 节点初始为 `frozen`，暗示这是"可放下"的部分

### 7.4 节点 urgencyStage

- urgent 方案的前 2 节点：`hot`
- 其他全部：`calm`
- 不要让节点级别的 urgency 比卡片级别更激进

## 8. proof 模块的 AI 行为

proof 不是 AI 的"创作物"，是"行为记录的格式化"。AI 只在以下两处生成自然语言：

### 8.1 lastAction / nextSuggestion

每条 ProofRecord 都需要这两个。模板：

| 触发场景 | lastAction | nextSuggestion |
|---|---|---|
| 选方案 | `选择{方案名}并生成任务流` | `进入 deck，先完成第一张最小行动卡` |
| 双击计时 | `开始计时：{卡 title}` | `完成这张卡，或下滑查看状态后选择冻结` |
| 三击燃烧 | `快速燃烧启动：{卡 title}` | `把燃烧当作提醒，完成最小动作或先冻结` |
| 完成卡 | `完成：{卡 title}` | `进入下一张卡，保持单卡节奏` |
| 冻结 | `冻结：{卡 title}` | `稍后从 reschedule queue 恢复，不需要重新理解目标` |
| 全部完成 | `奖励卡生成：{卡 title}` | `查看 proof summary，并决定下一组 deck` |

### 8.2 summaryDocument（一段总结）

读 proof 列表，生成一段 80-150 字的文字。包含：

- 今天留下了几条证据
- 多少完成 / 多少冻结 / 多少燃烧
- 一句"什么节奏最有效"的建议（基于完成卡的平均时长）

不要写"加油""继续努力"这类。要写有信息量的复盘。

例：
> 今天你已经留下 5 条行动证据，其中 2 个目标进入完成或奖励状态，1 张卡片被温柔冻结。你在 1 张卡片上使用了燃烧节奏，最适合继续推进的是 10 分钟内能结束的小任务。

## 9. 反例库（AI 绝对不能输出的形态）

### 9.1 卡片 title 反例

| 错 | 为什么 | 改成 |
|---|---|---|
| `学习数学` | 描述不是动作 | `用 25 分钟做完上次的错题本第 1 页` |
| `完成作业` | 范围不可验证 | `用 10 分钟写出最低可交版本` |
| `好好准备考试` | 含糊 | `今晚先确认数学考试的范围和题型` |
| `背单词` | 没量化 | `选 10 个最不熟的单词写到纸上` |

### 9.2 三方案反例

| 错 | 为什么 |
|---|---|
| 三个方案 steps 完全一样，只是 estimatedTime 不同 | 没有差异化哲学 |
| urgent 方案出现"冻结" | 与方案哲学冲突 |
| 三个方案都不到 4 步 | 违反前端契约（PlanOptionCard 期待 4 步） |
| 方案名不是"方案一/二/三" | 前端用下标渲染按钮文案 |

### 9.3 goalUnderstanding 反例

| 错 | 为什么 |
|---|---|
| `好的，你要明天考数学。` | 回显，没有重新框定 |
| `任务已收到，准备执行。` | AI 客服腔 |
| 长达 200 字的展开 | 标题区放不下，会换行难看 |
| 直接输出 markdown 列表 | 前端是单段文字渲染 |

### 9.4 时间锚反例

| 错 | 为什么 |
|---|---|
| `deadlineLabel: ""` | 前端 chip 显示空 |
| `deadlineLabel: "2025-05-16T20:00:00Z"` | 不是压力感表达 |
| `availableWindow: "尽快"` | 没起止 |
| 三个时间字段说同一件事 | 没区分 deadline / window / start 三个语义 |

### 9.5 卡组反例

| 错 | 为什么 |
|---|---|
| 第一张卡是"复盘上次进展" | 启动卡必须是"立刻可做"，不是反思 |
| 6 张卡都是 calm | 至少首卡或某张应有压力感，否则像 todo |
| 卡组没有收尾卡 | 没有"完成感"出口 |
| 元任务被拆成 5 张卡 | 过度拆解，反而增加摩擦 |

## 10. 与代码的对应关系

| 本规约章节 | mock-ai.ts 函数 | 替换为真 LLM 时的处理 |
|---|---|---|
| §1 复杂度 + §2 轨道 | `mockAnalyzeInput` 的关键词分支 | LLM 输出结构化 JSON `{ track, complexity }` |
| §3 goalUnderstanding | `mockAnalyzeInput` 的 `goalUnderstanding` 字段 | 由 LLM 写，受 §3.2 模板约束 |
| §4 三方案 | `mockGeneratePlanOptions` | LLM 必须返回 3 元素数组，受 §4.1-4.4 约束 |
| §5 时间锚 | `mockAnalyzeInput` 的三个 label 字段 | 受 §5.2 默认值表兜底 |
| §6 卡片字段 | `mockGenerateDeckFromPlan` + `makeAction` | LLM 返回卡数组，server 侧验证字段完整性 |
| §7 task flow | `mockGenerateTaskFlow` | 同上 |
| §8 proof 文案 | `mockGenerateProofSummary` + 各 store action 内联模板 | 复杂度低，可保留模板化生成 |

**校验层建议**：真 LLM 接入时加一层 `validateAIOutput()`：

- 方案数必须 3
- 每方案 steps 必须 4
- 三个时间字段必须非空
- urgencyStage / damageEffect 必须在枚举内
- 节点数 ≤ 4，卡片数 ≤ 6

不通过时让 LLM 重试一次，仍不通过则降级到 mock 模板。

## 11. 维护

新增/调整规则时：
1. 先在本文加规则；
2. 再改 `lib/mock-ai.ts` 实现；
3. 真 LLM 上线后，本文成为 system prompt 的来源 / 评测用例的判分依据。

跟前端组件相关的硬性数字（卡上限 6、方案数 3、节点上限 4、4 步 steps）受前端代码控制。改这些数字 = 改前端 + 改本文，**不能只改一边**。
